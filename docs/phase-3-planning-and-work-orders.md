# Phase 3 — 생산계획과 작업지시

## 1. 범위

Phase 3는 기준정보를 실제 생산 실행 흐름에 연결한다.

- 관리자의 생산계획 등록과 확정
- 확정된 계획을 하나 이상의 작업지시로 분할
- 활성 공정과 활성 `WORKER` 배정
- 역할별 작업지시 조회
- 배정된 작업자의 작업 시작
- 검색, 상태 필터, 페이지네이션

생산실적 등록, 작업 완료, 대시보드 수량 집계는 Phase 4에서 구현한다. 따라서 이번 단계에서 작업 시작은 가능하지만 완료 명령은 노출하지 않는다.

## 2. 상태 전환

### 생산계획

| 현재 상태 | 명령 | 다음 상태 | 허용 역할 | 서버 규칙 |
|---|---|---|---|---|
| `DRAFT` | 확정 | `CONFIRMED` | ADMIN, MANAGER | 한 번만 가능 |
| `CONFIRMED` | 확정 | 거부 | ADMIN, MANAGER | 409 응답 |

확정 후 계획의 품목, 납기일, 목표수량을 수정하는 API는 제공하지 않는다. 수정 이력이나 계획 취소가 필요한 시점에 별도 명령으로 확장한다.

### 작업지시

| 현재 상태 | 명령 | 다음 상태 | 허용 역할 | 서버 규칙 |
|---|---|---|---|---|
| `WAITING` | 작업 시작 | `IN_PROGRESS` | 배정된 WORKER | 배정 사용자 ID 일치 필요 |
| `IN_PROGRESS` | 작업 시작 | 거부 | WORKER | 중복 시작 409 응답 |
| `COMPLETED` | 작업 시작 | 거부 | WORKER | Phase 4에서도 재시작 금지 |

`COMPLETED`는 다음 단계의 마이그레이션 없이 완료 기능을 추가할 수 있도록 스키마와 enum에만 예약했다.

## 3. 데이터 관계

```text
product 1 ─── N production_plan 1 ─── N work_order N ─── 1 production_process
                                      │
                                      └────────────── N ─── 1 app_user(WORKER)
```

- 생산계획은 한 품목과 목표수량을 가진다.
- 한 생산계획은 여러 작업지시로 분할할 수 있다.
- 작업지시는 공정 하나와 담당 작업자 한 명을 가진다.
- 작업지시 목표수량 합계는 생산계획 목표수량을 초과할 수 없다.
- 업무 참조는 화면용 번호 문자열이 아니라 UUID 외래키로 유지한다.

`V3__create_planning_and_work_orders.sql`은 번호 고유 제약, 양수 수량 제약, 상태 제약, 상태와 시작·완료 시각의 일관성 제약을 둔다. 현재 조회 조건에 맞춰 계획 상태·납기일, 작업지시 계획, 담당자·상태에만 인덱스를 추가했다.

## 4. 동시성 및 트랜잭션

- 계획 확정은 생산계획 행을 pessimistic write lock으로 읽고 상태를 바꾸는 단일 트랜잭션이다.
- 작업지시 등록은 생산계획 행을 같은 방식으로 잠근 뒤 기존 지시수량 합계를 계산한다. 같은 계획에 대한 동시 등록 요청은 직렬화되므로 둘 다 잔여수량을 사용해 초과 배정하는 상황을 막는다.
- 작업 시작은 작업지시 행을 잠근 뒤 배정 사용자와 상태를 검사하고 시작시각을 기록한다. 동시 중복 시작 중 첫 요청만 성공한다.
- JPA `@Version`은 모든 엔티티에 유지해 잠금을 사용하지 않는 향후 수정 경로의 stale update도 방어한다.
- 번호는 날짜와 무작위 UUID 조각을 조합한 표시용 식별자이며 관계 키로 사용하지 않는다. 최종 중복 방지는 DB 고유 제약이 담당한다.

## 5. 권한 및 조회 범위

| API | ADMIN | MANAGER | WORKER |
|---|---:|---:|---:|
| 생산계획 조회·등록·확정 | 허용 | 허용 | 거부 |
| 활성 작업자 목록 | 허용 | 허용 | 거부 |
| 작업지시 등록 | 허용 | 허용 | 거부 |
| 작업지시 조회 | 전체 | 전체 | 본인 배정분만 |
| 작업 시작 | 거부 | 거부 | 본인 배정분만 |

메뉴 가시성과 별개로 Spring Security가 경로와 HTTP method를 검사한다. WORKER의 목록 범위와 작업 시작 소유권은 서비스에서 현재 인증 사용자의 UUID로 다시 제한한다.

## 6. API

| Method | Path | 의미 |
|---|---|---|
| `GET` | `/api/production-plans` | 계획 검색·상태 필터·페이지 조회 |
| `POST` | `/api/production-plans` | DRAFT 계획 등록 |
| `POST` | `/api/production-plans/{id}/confirm` | 계획 확정 |
| `GET` | `/api/workers` | 작업지시 배정용 활성 작업자 조회 |
| `GET` | `/api/work-orders` | 역할 범위에 따른 작업지시 조회 |
| `POST` | `/api/work-orders` | 확정 계획에 작업지시 등록 |
| `POST` | `/api/work-orders/{id}/start` | 배정 작업자의 작업 시작 |

상태 전환은 범용 상태 수정 API 대신 `confirm`, `start` 명령으로 표현한다. Entity는 반환하지 않고 관계 요약을 담은 Response DTO를 사용한다.

## 7. Phase 완료 기준

- 계획을 등록하고 확정할 수 있다.
- 확정 계획에 여러 작업지시를 만들되 합계가 계획 목표수량을 넘지 않는다.
- 작업지시에는 활성 공정과 활성 WORKER만 배정할 수 있다.
- WORKER는 본인 작업지시만 조회하고, 본인에게 배정된 대기 작업만 시작할 수 있다.
- 재확정, 초과 배정, 미배정 작업자의 시작, 중복 시작이 서버에서 거부된다.
- 백엔드 테스트·패키징과 프론트 린트·프로덕션 빌드가 통과한다.
- Compose 환경에서 Flyway V3 적용과 관리자→작업자 흐름을 확인한다.

## 8. 검증 결과

2026-10-01 기준으로 다음을 확인했다.

- WSL에서 백엔드 테스트 13건과 `bootJar`가 성공했다.
- Oxlint와 Vite 프로덕션 빌드가 성공했다. shadcn/ui 생성 파일의 Fast Refresh 권고 두 건 외에 린트 오류는 없다.
- Docker Compose에서 PostgreSQL, 백엔드, 프론트엔드가 정상 기동했으며 데이터베이스와 백엔드 health check가 통과했다.
- Flyway가 기존 V2 스키마에 V3 마이그레이션을 적용하고 Hibernate 스키마 검증을 통과했다.
- API에서 관리자 로그인, 계획 등록·확정, 작업지시 등록이 각각 정상 처리됐다.
- 계획의 잔여수량을 초과한 작업지시 등록은 409로 거부됐다.
- 작업자는 본인에게 배정된 작업지시만 조회했으며 작업 시작 후 상태가 `IN_PROGRESS`로 유지됐다.
- 같은 작업지시의 중복 시작은 409, 작업자의 생산계획 API 접근은 403으로 거부됐다.
- 브라우저에서 관리자 계획 등록 → 계획 확정 → 작업지시 배정 → 작업자 로그인 → 작업 시작 전 과정을 확인했다.
- 브라우저 네트워크 기록에서 계획 등록 201, 확정 200, 작업지시 등록 201, 작업 시작 200과 후속 목록 조회 200을 확인했다.
- 로그인, 관리자 작업지시, 작업자 작업지시 화면에 오류 오버레이나 콘솔 오류가 없고 역할별 메뉴가 올바르게 노출됐다.

위 결과로 Phase 3 완료 기준을 충족했다.
