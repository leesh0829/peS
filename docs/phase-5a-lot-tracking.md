# Phase 5A — 자재 LOT와 생산 LOT 추적

## 범위와 가상 공장 정책

Phase 5를 LOT 추적(5A)과 검사·불량코드(5B)로 분리한다. 이번 구현은 LOT 등록, 투입, 실적 기반 생산 LOT 생성 및 양방향 계보 조회만 포함한다. 검사 판정, 라벨, 재고 수불은 포함하지 않는다.

가상 소재 한 개로 부품 한 개를 만드는 단일 공정 시나리오다. 모든 자재 LOT 수량은 EACH 정수이며 LOT 추적 작업지시도 EACH 품목에만 생성할 수 있다. BOM, 대체자재 적합성, 중량 환산, 투입 취소·추가 수정은 구현하지 않는다. 동일 자재코드의 서로 다른 입고 묶음을 복수 LOT로 등록해 시연한다.

## 관계와 기존 데이터 보호

```text
MaterialLot N ── WorkOrderMaterial ── N WorkOrder
                                         │ 1
                                         │ N
                                  ProductionResult 1 ── 0..1 ProductLot
```

- 작업지시 하나에 여러 자재 LOT를 투입하고, 자재 LOT 하나를 여러 작업지시에 나눠 투입할 수 있다. 연결 엔티티에는 수량·등록자·감사시각을 기록한다.
- 실적 한 건마다 생산 LOT 한 건을 생성하므로 작업지시 하나에 여러 생산 LOT가 연결된다. 생산 LOT의 작업지시·품목·수량은 실적 관계를 통해 조회한다. 중복 저장하지 않는다.
- `work_order.lot_tracking_enabled` 기본값은 false다. 기존 작업지시·실적에는 가상의 LOT 계보를 소급 생성하지 않는다. 작업지시 생성 화면에서 추적을 명시적으로 선택한다. 선택하지 않은 기존 Phase 4 흐름도 유지된다.
- 생산 LOT는 양품만이 아니라 해당 실적의 생산수량 전체를 표현한다. 양품수량은 작업자가 기록한 수량이며 검사 합격이나 가용 완제품 재고를 의미하지 않는다.

## 상태·수량 규칙

| 작업지시 상태 | 자재 투입 | 시작 | 실적과 생산 LOT |
|---|---|---|---|
| WAITING, 추적 사용 | 배정 작업자만, 양수·중복 및 수량 초과 금지 | 투입 합계 = 목표수량일 때 가능 | 등록 불가 |
| IN_PROGRESS, 추적 사용 | 불가, 투입 관계 동결 | 중복 시작 불가 | 실적과 생산 LOT를 원자적으로 생성 |
| COMPLETED | 불가 | 재시작 불가 | 실적 추가 불가, 계보 조회 가능 |
| 추적 미사용 | 투입 불가 | 기존 Phase 3 규칙 | 기존 실적만 생성 |

동일 작업지시·자재 LOT 조합은 한 번만 투입한다. 여러 번 추가 입력하는 대신 처음 입력할 때 해당 묶음의 수량을 확정한다. 자재 LOT의 전체 작업지시 투입 합계는 최초 등록수량 이하여야 한다. 작업지시의 전체 자재 투입 합계도 목표수량 이하여야 한다.

투입은 취소·환입 없는 고정 배정 기록이다. 등록수량을 기준으로 중복 사용을 방지하지만, 재고원장이나 가용 재고 API를 제공하지 않는다.

## 계보의 정확도

정방향은 자재 LOT → 연결된 작업지시 → 실적 → 생산 LOT, 역방향은 생산 LOT → 실적 → 작업지시 → 투입 자재 LOT다. 이는 **작업지시 단위 잠재 계보**다. 예를 들어 자재 두 LOT와 생산 두 LOT가 같은 작업지시에 연결되면, 각 생산 LOT에는 두 자재 LOT가 모두 표시된다. 개별 생산 LOT에 각 자재가 정확히 몇 개 들어갔는지는 추정하거나 배분하지 않는다. 화면에 이 한계를 명시한다.

작업자는 본인 배정 작업지시의 투입·생산 LOT만 조회한다. 자재 LOT 등록 목록은 공용 기준정보로 조회할 수 있지만, 자재 정방향 계보에서 다른 작업자의 연결은 제외한다. 관리자·생산관리자는 전체 계보를 조회한다.

## DB와 트랜잭션

Flyway `V5__create_lot_tracking.sql`은 추적 선택 컬럼과 `material_lot`, `work_order_material`, `product_lot`을 추가한다. 기존 V1~V4는 수정하지 않는다. LOT 번호와 실적-생산 LOT 관계에 고유 제약, 연결 관계에 외래키와 `(work_order_id, material_lot_id)` 고유 제약을 둔다. 수량은 양수 CHECK로 보강한다.

- 투입: 작업지시 행 잠금 → 소유권·대기 상태 확인 → 자재 LOT 행 잠금 → 작업지시/자재 누적합 검사 → 연결 행 저장. 여러 작업지시가 같은 자재 LOT를 투입하더라도 자재 행 잠금 후 합계를 다시 확인한다. 잠금 순서는 역전하지 않는다.
- 시작: 기존 작업지시 행 잠금 안에서 추적 사용 시 자재 합계가 목표와 같은지 확인한다. 투입과 시작은 같은 작업지시 잠금을 사용한다.
- 실적: 기존 작업지시 행 잠금·수량 검증·실적 저장에 생산 LOT 생성을 같은 트랜잭션으로 포함한다. 생산 LOT 저장이 실패하면 실적도 롤백된다.
- 조회: read-only 트랜잭션 안에서 DTO를 생성한다. Entity를 API 응답으로 반환하지 않는다.

조회 요구에 따라 최신순 LOT 목록 인덱스와 자재 LOT별 연결 인덱스를 둔다. 작업지시별 연결은 복합 고유 제약의 앞 컬럼, 실적별 생산 LOT는 고유 제약의 인덱스를 사용한다.

기존 Spring Boot 4.1.1 / Java 21 / PostgreSQL 18 / React·Vite 버전을 유지했고 새 라이브러리를 추가하지 않았다. 구현 전 [Spring Data JPA 잠금 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html)와 [PostgreSQL 18 제약 문서](https://www.postgresql.org/docs/18/ddl-constraints.html)를 확인했다. 행 간 누적합 제한은 CHECK가 아닌 잠금 안의 서비스 검증으로 처리한다.

## API

| API | 권한·용도 |
|---|---|
| GET /api/material-lots | 모든 역할, 검색·최신순·페이지네이션 |
| POST /api/material-lots | ADMIN/MANAGER, 가상 자재 LOT 등록 |
| GET /api/work-orders/{id}/materials | 관리자 전체, 작업자 본인 배정분 |
| POST /api/work-orders/{id}/materials | 배정 WORKER, 대기 지시에 투입 |
| GET /api/product-lots | 관리자 전체, 작업자 본인 배정분, 검색·최신순·페이지네이션 |
| GET /api/material-lots/{id}/trace | 자재 정방향, 역할별 연결 필터 |
| GET /api/product-lots/{id}/trace | 생산 역방향, 다른 작업자 소유 LOT는 403 |

작업지시 생성 요청에 `lotTrackingEnabled`를 추가했다. 누락하면 false여서 기존 요청과 호환된다. LOT 번호는 가상 ML-/PL-접두사·날짜·임의 suffix로 서버에서 생성한다.

## 화면 시연

1. 관리자 로그인 → LOT 추적 → 자재 LOT에서 동일 가상 자재코드 `RAW-001`로 6개·4개 두 묶음을 등록한다.
2. EACH 품목 계획 10개를 확정하고 작업지시 생성에서 LOT 추적을 선택해 worker에게 배정한다.
3. worker 로그인 → 내 작업지시 → 해당 행의 자재 LOT 버튼 → 두 자재 LOT를 각각 6개·4개 투입한다. 합계가 10이어야 시작할 수 있다.
4. 작업 시작 → 실적을 6개(양품 5·불량 1), 4개(양품 4·불량 0) 등록한다. 생산 LOT 두 건이 생성된다.
5. 목표 달성 후 완료 → LOT 추적에서 생산 LOT 역방향과 자재 LOT 정방향을 각각 조회한다.
6. 관리자로 재로그인해 전체 계보와 집계를 확인한다. LOT 생성이 Phase 4 집계에 별도 수량을 더하지 않는다.

## 완료 기준과 검증 상태

5A의 완료 기준은 다건 투입·공유 자재 과다 투입 방지, 투입 동결, 실적당 생산 LOT 생성과 양방향 조회, 역할 경계, 기존 Phase 4 호환, Flyway V5 실제 적용 및 브라우저 시연 확인이다. 5B는 생산 LOT에 독립된 검사 사건과 복수 불량코드를 연결하는 후속 단계다.

WSL에서 `bash scripts/validate.sh`의 백엔드 테스트 35건·bootJar, 프론트 린트·TypeScript·프로덕션 빌드가 통과했다. 기존 shadcn Fast Refresh 경고 2건은 남아 있다. Linux Docker CLI가 없어 Compose 검증은 건너뛰었다. Windows 경로의 Docker 실행 파일은 WSL에서 호출하지 않았다.

재기동 후 `node scripts/verify-phase5a.mjs`로 실제 API·DB 통합 검증을 실행한다. 이 스크립트는 가상 계획 1건, 작업지시 2건, 자재 LOT 2건, 실적 4건과 생산 LOT 4건을 남긴다. 공유 자재 LOT 동시 투입의 201/409 처리, 수량·권한·중복·시작 후 투입 거부, 다대다 계보 및 집계 증가량을 검사한다. 스크립트 구문은 확인했지만 실제 V5 API 실행은 아직 확인 전이다. 다른 실적 입력 없이 개발 환경에서 단독 실행해야 한다.

실제 V5 적용·통합 스크립트 실행·새 화면 브라우저 검증을 확인하기 전에는 5A 전체 완료로 표시하지 않는다.
