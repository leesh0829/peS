# Phase 6 — LOT 식별 라벨 발행·재출력 이력

범위는 출력용 LOT 식별 데이터 생성, 미리보기 및 발행 이력이다. 실제 프린터 연동·인쇄 성공 확인·PDF·바코드·재고 수불은 제외한다. 발행 완료는 인쇄 성공이나 품질 합격을 보장하지 않는다.

## 규칙과 관계

완료된 작업지시의 생산 LOT만 최초 발행할 수 있다. ADMIN/MANAGER가 발행하며 WORKER는 본인 배정 LOT의 이력만 조회한다. 최초 발행은 한 번만 허용하고 재출력은 별도 명령으로 사유(1~500자)를 받는다. 기존 미리보기 조회는 새 발행 이력을 만들지 않는다.

`ProductLot 1:N LabelEvent`, `User 1:N LabelEvent(issuedBy)` 관계다. Flyway V7에서 LOT+순번 고유 제약, 양수 수량·순번 및 재출력 사유 CHECK를 적용한다. 품목 코드·명칭, 생산수량, LOT번호, 발행자명은 발행 당시 스냅샷이다. 재출력은 최초 스냅샷을 그대로 복사한다. 이력 수정·삭제 API는 없다.

쓰기 트랜잭션은 LOT 행 잠금 → 완료 상태·최근 순번 확인 → 발행자 조회 → 새 이력 저장/flush이다. 같은 LOT의 최초 발행은 직렬화되어 중복 요청 중 하나만 성공한다. 재출력 동시 요청은 각각 별도 사건으로 순번이 증가한다. 생산·검사·재고는 변경하지 않는다. 잠금 구현은 [Spring Data JPA 공식 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html)를 확인했고 기존 버전·의존성을 유지했다.

## API와 화면

- GET `/api/product-lots/{id}/labels?page=0`: 역할별 소유 범위 확인, 최근 순번 우선 20건 페이지 조회.
- POST `/api/product-lots/{id}/labels/issue`: 최초 발행, 201 응답.
- POST `/api/product-lots/{id}/labels/reprint`: `{reason}` 입력, 재출력 이력 생성, 201 응답.

새 메뉴 대신 LOT 추적 → 생산 LOT → 역방향 조회 상세에 기존 shadcn/ui 버튼·입력·페이지네이션으로 연결했다. 재출력 사유와 오류 표시를 제공하고 저장 성공 후 이력 쿼리를 무효화한다. 인쇄 성공 상태는 구현하지 않는다.

## 시연·검증

관리자 생산 LOT 상세에서 최초 발행 → 라벨 미리보기 → 사유 입력 후 재출력 → 순번·발행자·시각·사유 확인 → 작업자 조회를 시연한다. 이력 생성 전후 생산 집계가 같아야 한다.

자동 테스트는 작업자 쓰기, 사유 누락, 완료 전 발행, 최초 발행 없는 재출력, 중복 최초 발행 거부 및 스냅샷·수량 불변을 다룬다. 실제 Docker V7 적용 및 브라우저 시연 확인은 재빌드 후 수행해야 하며 현재 대기 상태다.

2026-10-02 WSL에서 `bash scripts/validate.sh` 성공: 백엔드 테스트 59개(새 라벨 테스트 7개 포함) 및 bootJar, 프론트엔드 lint·타입 검사·프로덕션 빌드 통과. 기존 Button/Badge의 Fast Refresh 경고 두 건은 남아 있다. Linux Docker CLI 부재로 Compose 검증은 건너뛰었다. `.git/index.lock` 생성이 읽기 전용 제한으로 실패하여 이 변경의 커밋·푸시는 아직 수행하지 않았다.

이후 사용자 Windows 실행 결과에서 `c43c56c` 커밋·푸시와 Flyway V7 적용 및 healthy 상태를 확인했다. 실제 API에서도 최초 발행 동시 요청 201/409, 동시 재출력 순번 2/3, 사유·스냅샷 보존, 작업자 발행 거부·이력 조회 및 대시보드 불변을 확인했다. 개발 DB에 가상 발행 이력 세 건을 보존했다. 브라우저 도구 승인이 차단되어 라벨 화면 시연은 아직 미확인이다. 이전 문단의 커밋·V7 대기 상태는 당시 기록이며 현재 잔여 검증은 화면 점검이다.

2026-10-08 재기동 후 Playwright에서 라벨 화면을 확인했다. ADMIN의 기존 이력 조회·미리보기는 이력 수를 유지했고 재출력 사유 입력·저장 후 새 순번 #4와 동일 사유를 API 재조회로 확인했다. MANAGER는 다른 완료 LOT에서 최초 발행해 순번 #1·발행자명·미리보기를 확인했다. 빈 사유에서는 재출력 버튼이 비활성화됐다. WORKER는 본인 LOT의 #4 이력을 볼 수 있으나 발행 입력은 표시되지 않았다. MANAGER/WORKER 모두 사용자 관리 메뉴가 없고 관리 API 직접 요청은 403이었다. 콘솔에 기록된 오류는 이 의도적인 403 요청뿐이었다. 가상 발행 이력 두 건을 추가·보존했으며 시연 종료 후 로그아웃했다. 라벨 화면 확인은 완료했지만 모든 업무 폼·모바일·페이지 경계까지 검증한 것은 아니다.
