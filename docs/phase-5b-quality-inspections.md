# Phase 5B — 검사와 불량코드

## 범위와 시연

관리자 또는 관리자가 아닌 MANAGER가 불량코드를 등록하고, 완료된 작업지시의 생산 LOT를 전수검사한다. 작업자는 자신에게 배정된 작업지시의 검사 결과만 조회한다. 검사·불량 화면에서 검색, 판정 필터, 페이지 조회, 상세 및 입력 오류를 확인하고 LOT 상세에서도 검사 결과를 조회한다.

시연 순서: 관리자 기준정보·계획·작업지시 등록 → 작업자 자재 투입·작업 시작·실적 등록·작업 완료 → 관리자 불량코드 등록·LOT 검사 → 작업자 LOT 상세 확인 → 관리자 생산 집계 확인. 기존 생산 집계는 검사 등록 전후 동일해야 한다.

재검사, 검사 수정·삭제, 불량코드 수정·삭제, 샘플 검사, 라벨 및 재고 수불은 제외한다. 완료와 검사 합격은 별개이고 어느 쪽도 가용 재고를 증가시키지 않는다.

## 수량과 판정

- 검사수량은 해당 생산 LOT 실적의 생산수량 전체와 같아야 한다.
- 검사수량 = 합격수량 + 불합격수량. 불합격수량은 서버에서 차이로 계산한다.
- 불량내역 수량 합계 = 불합격수량. 동일 코드 중복과 음수·0인 불량내역을 거부한다.
- 합격수량은 실적의 양품수량을 넘을 수 없다. 이미 생산 불량으로 기록한 수량을 합격으로 바꾸지 않는다.
- 생산 양품 중 추가 불량을 발견할 수 있다. 검사 결과는 생산실적을 덮어쓰지 않는 독립 기록이다.
- 불합격수량 0이면 PASS, 양수이면 FAIL. 판정은 클라이언트가 지정하지 않는다.
- 생산 LOT당 검사 한 건만 허용한다. 미검사 → PASS 또는 FAIL이며 후속 전환은 없다.

예: 생산 10, 생산 양품 9, 생산 불량 1인 LOT를 검사해 합격 8, 검사 불합격 2로 기록할 수 있다. 불량코드별 수량은 합계 2여야 한다. 생산 집계는 계속 10/9/1이다.

## DB 관계와 트랜잭션

`ProductLot 1 — 0..1 InspectionResult 1 — N InspectionDefect N — 1 DefectCode`

`User 1 — N InspectionResult(inspectedBy)`

Flyway V6에서 세 테이블을 추가한다. LOT별 검사 고유 제약, 검사별 불량코드 고유 제약, 외래키와 행 단위 수량·판정 CHECK를 둔다. 여러 불량행의 합계 및 생산실적과의 비교는 서비스 트랜잭션에서 검증한다. 목록 조회를 위한 검사 생성일 인덱스만 추가한다. 시연 데이터는 마이그레이션에 넣지 않는다.

검사 등록은 생산 LOT 행 잠금 → 작업지시 완료·기존 검사·전수 수량 확인 → 검사자 및 불량코드 조회 → 검사와 불량내역 저장/flush를 한 트랜잭션으로 실행한다. 같은 LOT의 동시 요청은 잠금으로 직렬화하고 고유 제약도 최종 방어선으로 둔다. 완료된 작업지시는 재시작할 수 없으며 검사에서 실적·재고를 변경하지 않는다. 페이지 조회는 컬렉션 fetch join 대신 to-one 조회와 불량내역 배치 로딩을 사용한다.

잠금은 [Spring Data JPA 공식 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html), 제약은 [PostgreSQL 18 공식 문서](https://www.postgresql.org/docs/18/ddl-constraints.html)를 확인했다. 기존 프로젝트 의존성 버전을 유지하며 새 라이브러리는 추가하지 않았다.

## API

| API | 권한 및 용도 |
| --- | --- |
| GET /api/defect-codes | 모든 역할, 검색·페이지 조회 |
| POST /api/defect-codes | ADMIN/MANAGER, 코드 등록 |
| GET /api/inspection-candidates | ADMIN/MANAGER, 완료·미검사 LOT 검색 |
| GET /api/inspections | 모든 역할, 작업자는 본인 배정 범위, 검색·판정·페이지 조회 |
| GET /api/product-lots/{id}/inspection | 모든 역할, 작업자는 본인 배정 범위, 미검사는 inspection:null |
| POST /api/product-lots/{id}/inspect | ADMIN/MANAGER, 전수검사 등록 |

Request/Response DTO, Bean Validation, 기존 일관된 오류 응답과 세션/CSRF 인증을 사용한다. 메뉴 표시와 무관하게 API에서 역할 및 배정 범위를 검증한다.

## 검증과 완료 기준

자동 테스트는 수량 합계 불일치, 음수, 불량코드 중복, 합계 오버플로, 부분 검사, 생산 불량의 합격 처리, 완료 전 검사, 중복 검사, PASS/FAIL, 생산수량 불변, 작업자 쓰기 및 타인 LOT 조회 거부를 다룬다.

WSL의 `bash scripts/validate.sh`로 백엔드 테스트·bootJar 및 프론트엔드 lint·타입 검사·빌드를 확인한다. 기존 UI 컴포넌트 Fast Refresh 경고는 빌드 실패와 구분한다.

실제 Docker 환경에서는 재빌드 후 V6 적용, 검사 대기 LOT 조회, PASS/FAIL 등록, 중복 요청 거부, 역할별 조회, LOT 상세 연결과 생산 집계 불변을 확인해야 한다. 이 실제 DB·브라우저 확인 전에는 Phase 5B 전체 완료로 간주하지 않는다.

### 2026-10-01 실제 실행 확인

- 사용자 제공 Docker 로그에서 PostgreSQL·백엔드 healthy 및 Flyway V6 적용 성공을 확인했다.
- WSL에서 `node scripts/verify-phase5b.mjs`를 실행해 실제 API 검증을 통과했다. 수량 합계·음수·부분 검사·생산 불량의 합격 처리·중복 코드 거부, 작업자 관리 API 403, 동시 등록 201/409, PASS/FAIL 저장, 작업자 LOT별 검사 조회, 판정별 목록, 검사 대기 목록 제외 및 대시보드 불변을 확인했다.
- Playwright로 브라우저 로그인, 검사 목록의 두 판정 및 불합격 상세의 복수 불량내역을 확인했다. 로그인 후 검사 화면 콘솔 오류 0건이며 화면도 캡처해 확인했다. 모든 입력 폼·모든 역할의 화면 동작을 검증했다는 의미는 아니다.
- 검증은 기존 Phase 5A 가상 LOT 두 건에 검사 두 건과 가상 불량코드 두 건을 추가했다. 데이터는 개발 DB에 보존한다. 스크립트 재실행에는 새로운 미검사 6/5/1 및 4/4/0 LOT가 필요하며 `node scripts/verify-phase5a.mjs`로 생성할 수 있다. 실제 업무 데이터가 있는 환경에는 실행하지 않는다.
